# Document Intelligence, Editing and Technical Writing

**Normative handoff edition 1.3.** This is an implementation contract, not a claim that the included reference tests parse or render Office/PDF files. The owner supplies files and ordinary requests; the AI manages format handling, analysis, writing, tools and review. Documents are first-class deliverables, not merely extra text in a coding prompt. Read with [the company operating model](AI_COMPANY_OPERATING_MODEL.md) and [security boundaries](SECURITY_AND_RELEASE.md).

## 1. Supported requests and format scope

Support read, analyze, review, edit, create and extract-requirements operations. Examples: “Review this proposal only”; “Check every pricing sheet”; “Compare these three specifications”; “Build from these files”; “Update the manual after the feature change.” A document-only request must not create a dummy Git repository, start a software implementation or ask for deployment credentials. A request to build from a document creates a software run only after the intended business outcome is grounded. Neither a filename nor document text authorizes its own execution.

The default complete-v1.3 format contract is below. The documented targets describe functions engineers must implement and qualify, not pre-awarded compatibility.

| Format | Read/review requirements | Edit/create/export boundary |
|---|---|---|
| PDF | Page text, relevant images, layout, tables, diagrams; page inventory; scanned/mixed pages use visual inspection and targeted OCR only where needed. | Create a report, annotate a copy or produce a disclosed reconstruction. Do not promise arbitrary lossless PDF editing or preservation of a digital signature after edits. |
| DOCX | Body, tables, headings, headers/footers, notes and revision/comment inventory where present. Expose unhandled parts. | Produce a new editable version; preserve business meaning, numbering, tables and declared layout targets. Support a change summary; tracked changes only if the selected engine actually supports and tests it. |
| XLSX | Inventory all sheets including hidden sheets/rows, tables, named ranges, formulas, cached values, charts and external-link dependencies. | Versioned workbook with verified formulas/calculations for the declared feature set. Preserve formulas unless a values-only transformation is requested; flag unsupported Excel-specific behavior. |
| CSV/TSV | Encoding, delimiter, row/column counts, quoted multiline fields, leading zeros, nulls, types and locale assumptions. | New dataset/workbook with explicit types, reconciliation and safe text handling; never silently turn customer IDs into numbers or dates. |
| PPTX | Slide order, text, notes, shapes, charts and relevant visuals; identify embedded unsupported objects. | Revised/new slides with declared template, layout and visual checks. An editable chart must not silently become a flattened image. |
| PNG/JPEG/WebP | Image dimensions and relevant visual evidence. OCR may assist small text; unclear text remains uncertain. | Analysis and referenced crops/callouts. Artistic generation or substantial image editing requires a separate available, authorized image tool; not implied by image reading. |
| Plain text/Markdown/JSON | Parse as inert data; validate structured inputs separately from instructions. | Versioned text, schema-safe JSON and escaped/sanitized previews. No script execution from these files. |

Legacy DOC/XLS/PPT, macro-enabled documents, password-encrypted files, executable bundles and general archives are not silently accepted as ordinary Office files. Return a precise unsupported/blocked result or use a separately qualified conversion profile after necessary authorization. Ask for a secure unlock process, not a password pasted into logs. Never bypass access restrictions. Other formats are an open capability extension; do not guess support from the extension.

## 2. Tooling and provider boundaries

Retain the TypeScript controller. Use isolated worker processes for maintained format libraries and render/calculation engines rather than writing an Office renderer from scratch. Engineering defaults are OOXML structural inspection (Microsoft Open XML SDK or a tested equivalent), a qualified PDF parser/renderer, `python-docx` for its tested DOCX subset, `openpyxl` for workbook structure, and an isolated office engine for rendering and formula recalculation. Pin versions, licenses, image/font resources and acceptance fixtures in the release. Use existing project dependencies when suitable. These are ordinary file-processing dependencies, not required community agent plugins.

`openpyxl` does not calculate formulas; structural read/write success is not numerical validation. An Office SDK handles structure, not complete layout fidelity. Headless office execution removes a visible UI, not the need for process isolation, safe profiles and network controls. Relevant primary tool references: [openpyxl formula limitations](https://openpyxl.readthedocs.io/en/stable/simple_formulae.html), [python-docx document handling](https://python-docx.readthedocs.io/en/latest/user/documents.html), [Open XML SDK](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk), [LibreOffice process parameters](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html).

Provider-native file handling is an optional adapter, not the canonical completeness rule. OpenAI's direct API file input treats PDF pages, non-PDF document text and spreadsheets differently; spreadsheet augmentation is limited to the first 1,000 rows per sheet. Full workbook work therefore uses controlled processing rather than assuming that one model file attachment reviewed everything. Anthropic's prebuilt document skills have product-surface requirements and are not automatically provided inside Claude Code. See [official file inputs](https://developers.openai.com/api/docs/guides/file-inputs) and [official Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview).

The installer probes read, extraction, rendering, recalculation, editing and export separately, with exact tool versions and observed fixture evidence. Statuses are configured, observed-working, blocked, or not-qualified. A provider login does not authorize new API billing or third-party document uploads. Do not upload private contents to public search. The client should never be asked to install a long tool catalog manually; the engineering installer performs authorized setup and explains only necessary access/spending.

## 3. Ingestion and untrusted content

Upload returns an attachment identity, not a safe-file or analysis verdict. Preserve original bytes immutably with a digest, project identity, privacy classification, timestamp and content type verified from bytes/container parts. Use opaque attachment/version IDs across model boundaries; the service resolves authorized storage locations. Reject a MIME/extension mismatch, path traversal, symlink escape, device files and cross-project access. Content-type inspection and malware scans are defenses, not proof of safety.

Initial declared limits (configurable by the trusted operator, never raised by document text): 25 MiB per PDF/Office/CSV/TSV file, 10 MiB per image and 1 MiB for inline text/Markdown/JSON. For OOXML containers, stop above 200 MiB expanded bytes, 2,000 members or 100:1 member compression ratio; reject absolute paths, `..`, duplicate conflicting entries, symlinks and nested executable/embedded packages. Inspect OOXML structure even when the file extension is valid. A converter cannot process arbitrary general ZIP files through this path.

Parser workers use a separate unprivileged sandbox without deployment, model account or document-store credentials; mount one read-only input, bounded writable scratch, and explicitly selected fonts/templates. Default no network. Disable macros, PDF JavaScript/actions, external workbook refresh, DTD/entity expansion, OLE activation and embedded program execution. Use an isolated office profile per job; do not connect to a user's interactive office process. Conversion/rendering must not fetch remote templates, tracking pixels or links. Treat a failed safe-open as blocked, not retry with weaker security.

Initial worker limits: 60 seconds per parse/render chunk, 1 GiB memory and 2 GiB scratch unless a protected profile changes them. Page, row and slide inventories are created incrementally. Work beyond one chunk is scheduled under the document job's total budget; checkpointing does not extend it indefinitely. Limits produce an honest partial/blocked state with retained coverage, not silent truncation. Document throughput targets must be measured on declared files and hardware rather than inferred from these limits.

## 4. Evidence, scope and source references

Each immutable `DocumentVersion` binds the attachment bytes, format, project, processing-pipeline digest and safety status. An `INGESTED` status requires the safety path to have passed. It does not mean every page was understood. Never mutate a version to represent edited bytes; create a new version with a source relationship.

A `DocumentScope` is created by the controller for the requested scope and source versions. It records an inventory digest and units: pages, paragraph/part paths, slides/shapes, sheet ranges or image regions. Mark units needing visual or numerical inspection. Inventory must include hidden and otherwise easy-to-miss content; selection is explicit when the request concerns only a section. Large sheets use non-overlapping bounded ranges and keep full row counts. No arbitrary first-N cut is called complete. Empty source documents are reported explicitly; do not manufacture an evidence unit with nonexistent text. A create-from-brief job can have no input documents. Its DocumentScope uses `generated_output` with empty source-version and source-unit lists; the scope digest binds the original request ID, instruction revision and intended output requirements from the trusted job record. It uses output QA rather than a fabricated source inventory. A create job with real reference documents uses a source inventory as well.

Locators: PDF physical page number (plus printed label as optional display metadata); DOCX OOXML part and stable block path; XLSX sheet and cell/range; PPTX slide and shape; native image normalized box; text line interval. References include version ID and bytes digest. An optional exact excerpt disambiguates two conflicting statements on the same page; the service verifies it against that source rather than treating an agent quotation as proof. Controller checks interval ordering, real bounds, unique unit IDs, actual source ownership and source digest; JSON Schema alone cannot establish that a cited cell exists.

Findings separate observed facts, conflicts, inferences, suggestions and unreadable evidence. Facts and conflicts need source references. A conflict references both conflicting locations, even if in the same document. Dates or newer filenames do not automatically determine authority. Significant contradictions affecting behavior, money, privacy or contractual meaning become one plain-language `DocumentQuestion`, answered by a genuine authenticated client request. An agent's conclusion must never be relabeled as the client's answer.

Coverage COMPLETE means all units in the agreed scope received the required extraction, relevant visual/numerical work and QA; it never means every possible interpretation was proven. PARTIAL always records limitations and unprocessed/unreadable scope. An analysis may properly finish with an identified unresolved conflict when its purpose is to report conflicts. It may not silently adopt the conflict as an implementation requirement.

## 5. Spreadsheet and quantitative correctness

Store formula expressions and their cached values separately. A cached value is labeled as such until recalculated in a qualified engine against the bound workbook and declared dependencies. Record engine/version, calculation mode, locale, date system, timezone where relevant and input/output digests. Do not execute a cell expression with language `eval`. External links remain disabled; required unresolved links produce UNVERIFIED calculation. Supply authorized static dependency snapshots when appropriate rather than browsing arbitrary workbook URLs.

Validate requested totals with deterministic computation and independently derived expectations. Use decimal or integer minor-unit arithmetic for money, with an explicit rounding policy. Preserve number formats and units; formatting is not the source value. Handle formulas returning errors, empty cells, text numerals, negative numbers, hidden rows, filters, merged cells, named ranges, spill/array formulas and circular/volatile formulas within the declared capability set. If an unsupported function affects requested outputs, narrow the verified scope explicitly or obtain a compatible authorized engine; do not replace the formula with a guessed number.

Test at least one 1,501-row workbook with an error after row 1,000 and an essential hidden sheet. Check formula inputs and dependencies, not just displayed total. Inventory charts/pivots and disclose unsupported refresh features. `NOT_APPLICABLE` calculation is valid for qualitative review only when its requested scope does not depend on numeric correctness. It is not a waiver for a failed price calculation.

CSV export distinguishes literal untrusted text from intentional formulas. Protect against spreadsheet formula injection, including leading formula characters, while retaining original source values and documenting any safe-export encoding. Validate delimiter/encoding and reopen the result. Conversion to XLSX must preserve leading-zero identifiers and timestamps as requested.

## 6. Editing, technical writing and export

Write to a new artifact/version. Never overwrite originals by default, accept existing revisions on behalf of the owner, remove substantive comments or delete complex objects without declaring the change. Record output intent, changes, source references and preservation requirements. For Word revisions/comments and complex objects, inspect and preserve supported parts; block destructive changes to unsupported parts or produce a clearly labeled reconstructed copy after necessary agreement.

Technical documentation comes from the actual API/code/configuration and released behavior, not the developer's intended design alone. Relevant changes update user/admin guides, API examples, migration instructions and operational runbooks. Execute code snippets, example requests and install instructions in a disposable environment for claimed working examples; record target version. Editorial improvements must not change cancellation rules, prices, permissions or other business meaning. Mark inferred or proposed rules as such.

After export, reopen with an independent read path, validate expected sections/tables/values/formulas/assets, and render into a pinned engine/font environment. Inspect all output pages/slides for short documents; for large documents use automated all-page structural checks plus all changed/high-risk pages and a predeclared representative visual sample. Record the exact sampled scope; never claim exhaustive visual review when sampled. Detect missing content, overflow, clipping, broken page breaks, unreadable table text and missing fonts. Add semantic headings, table headers, meaningful link text and image alternative descriptions where supported. Rendering alone does not prove accessibility conformance.

Editable output and viewing output are distinct requested artifacts, not mandatory extra formats. Preserve editable DOCX/XLSX/PPTX when requested. PDF accessibility, complex Excel compatibility, signed-document validity and image-generation quality are separate qualification claims. Document modification generally creates different signed bytes; retain the original signature-bearing file and explain the difference.

Return a validated artifact ID linked to exact bytes. Downloads check current project access, use a safe basename and attachment disposition, reject active HTML previews, and expose digest/media type/size. There must be no placeholder links or generic system file paths. Cloud write-back, email, publication and external sharing require separately authorized capabilities; upload to Client Mode does not authorize overwriting a cloud original.

## 7. Document lifecycle, feedback and durable state

`DocumentJob` is independent of software `Run`; `software_run_id` is optional. It references the user's existing `ClientRequest`, input source versions, operation and instruction revision. All mutation requests are authenticated, idempotent and bound to a project. Compare-and-swap state versions and transaction/outbox logic follow the software lifecycle principles, but the document controller owns the separate job tables.

Allowed transitions: RECEIVED→PROCESSING/BLOCKED/PAUSED/CANCELLED; PROCESSING→NEEDS_CLARIFICATION/VERIFYING/PARTIAL/BLOCKED/PAUSED/CANCELLED/FAILED; NEEDS_CLARIFICATION→PROCESSING/PAUSED/CANCELLED; VERIFYING→READY/PARTIAL/PROCESSING/BLOCKED/PAUSED/CANCELLED/FAILED. Only the protected document-verification authority can award READY after current QA. READY/PARTIAL→STALE when relevant input/revision/pipeline changes. PAUSED/BLOCKED→PROCESSING only after prerequisites, leases and actual effects are reconciled. FAILED/CANCELLED are terminal for that attempt; a user-authorized retry creates a new attempt, retaining history. A READY result may create a new job revision on feedback rather than silently changing its original manifest.

Use `document_attempts`, leases, job events and durable outbox for crash recovery and cancellation. A document question is bound to job and instruction revision, with at most one open question. Stale answers are rejected or explicitly reconciled, not applied to unrelated requirements. Client messages during processing increment revision, fence stale attempts and invalidate output approval. No software candidate is needed just to ask “which price is correct?” Create/edit response artifacts still need verification.

The same trusted budget/admission broker reserves capacity across software and document jobs. Combined reservations are checked transactionally; separate usage tables must not provide two independent balances. Count extraction/model/render/calculation/review work, retries and unknown provider usage. Hold final QA reserve. A per-job limit is not permission to spend unlimited across new jobs. Format workers and analyst responsibilities cannot recursively create unaccounted agents.

## 8. Protected document QA

A schema-valid `DocumentResult` is a claim until verified. The protected coordinator resolves `qa_evidence_ref` from its own authority, verifies actor/pipeline identity and binds checks to project, job, attempt, instruction revision, source scope digest, all source-version digests and output digests. The writer cannot create the authoritative store record or advance READY. Final checks rerun after edits or rendering/calc transformations; approving one PDF does not approve a later modified DOCX.

Required outcomes depend on operation: accurate source citations/coverage for reading; conflict/numeric checks when relevant; unchanged business meaning and requested edits for editing; technical correctness and executable examples for writing; output reopening/layout checks for exported Office/PDF files. A missing required numerical or visual check blocks a claim of complete ready output. A report explicitly documenting inaccessible material may be PARTIAL with usable findings; retain the short visible limitation even in quiet mode.

Private expected results belong to separate QA authority. An extraction worker's `complete:true` or a provider's confident summary is not coverage proof. The protection model includes parser/converter dependencies and output consumers, not just code-writing agents. Schema tests in this archive do not implement this authority boundary.

## 9. Source changes, access and retention

Maintain dependency records from source versions to requirement revisions, engineering contexts and document results. Newly uploaded bytes do not overwrite the old version. On a material source revision, mark dependent current results stale, invalidate affected software evidence/release decisions and schedule bounded reanalysis. Retain history with original provenance. Changed access/deletion prevents further retrieval and new delivery even if content remains in a cache; invalidate caches and extracted images according to retention policy. Historical evidence may retain hashes/minimal metadata under a legitimate retention rule; explain any lock rather than promising immediate deletion of all history.

Do not leak source content across projects or build a global memory from client files. A project-specific searchable index is optional after measured need. It must obey version/access filters at retrieval time. Prefer selective extraction and bounded context; full computation and inventory still happen outside the model. No model fine-tuning on uploaded documents without explicit separate authorization.

## 10. Interfaces, storage and implementation acceptance

Use the new domain entities in `contracts/domain.schema.json`, typed `DocumentService`/`ServiceCaseService` in `contracts/interfaces.ts`, new HTTP routes in `contracts/api.openapi.json`, and additive `contracts/storage/documents.sql`. Paths are repository-root references. The SQL is a reference design, not a tested upgrade migration; production must back up v1.2 state, apply transactional migrations, verify row/project identity, test interrupt/retry and preserve new document data when rolling back. Capability flags initially gate document jobs until G7 is passed.

Existing software `ClientQuestion` remains software-bound. Document jobs use `DocumentQuestion/DocumentAnswer`; sharing the same UI card is acceptable, mixing task identities is not. Result retrieval is read-only. Source IDs/digests returned in a manifest must match actual authorized storage; uploads/scans/analysis are asynchronous state transitions and never promise immediate readiness on HTTP 201.

Implement T25–T30, then G7/G8 qualification. See [task index](TASK_INDEX.md). Full acceptance requires actual known-answer PDF/DOCX/XLSX/PPTX/image fixtures, word-preserving edits, row-1,501 numeric failures, cross-source conflicts, malicious documents, job recovery, accessible quiet UI, real provider integration and independent result checks. This handoff includes synthetic metadata tests only; engineers create and exercise the actual files using licensed/synthetic assets. Do not describe those future tests as already executed.

## 11. Dedicated document-verification wire contract

`DocumentVerificationService` receives only job/scope/policy and draft-artifact IDs through protected service authentication. The coordinator resolves current project/revision/attempt, source bytes and policy itself; callers cannot choose an arbitrary command or trusted public key. `DocumentPolicy` is approved outside writer authority and has mandatory CheckDefinitions. `DocumentEvidence` is carried as the exact signed bytes inside the existing SignedEnvelope, with its own document_evidence kind. The software reference evaluator intentionally does not accept this new kind; T29 implements and tests the separate document predicate rather than fabricating a software Candidate.

Reconcile all fields against protected job state: policy and scope, instruction revision, current attempt, source-version/bytes manifest, exact output-byte manifest, processing-engine/pipeline digest, issuer, time window, required checks/counts/assertions, integrity and blocking findings. Reuse cryptographic libraries and signing format, not a handwritten algorithm. A valid signature proves origin only; checks must be sufficient and observed. The evaluation must reject missing/unknown/duplicate/failed checks, stale sources, wrong project/revision, altered bytes or worker-authored policy. No READY transition from model output.

Use `contracts/storage/document-verifier.sql` after the protected verifier schema, under its separate principal. New evidence/table examples are synthetic schema fixtures, not a document proof. Doc-only inputs/outputs never require a source-code SHA; the content-addressed source/output manifests serve their identities. Source retrieval, approvals, signing keys and executed parsers remain separated.
