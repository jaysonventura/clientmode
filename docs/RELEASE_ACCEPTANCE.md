# Engineer-Owned Release Acceptance

Normative edition 1.3. This checklist is for the engineering team, not homework for the client. Every claim needs an artifact, command/observation, exact version/candidate, timestamp and responsible reviewer. All product rows below are **NOT EXECUTED by this handoff**. G0 reference tests do not fill them in.

## 1. Four separate approvals

| Approval | What it establishes | Who supplies evidence/authority |
|---|---|---|
| Toolkit qualification | This Client Mode build works on the declared provider/OS/task-family matrix | Engineering, independent QA, security/release owner |
| Generated-deliverable technical readiness | This application or document candidate meets its requirements and target/format-specific gates | Protected verifier plus proportionate specialist review |
| Client acceptance | The delivered experience matches the client's needs/taste | The actual authenticated client |
| Production release and health | The exact artifact is authorized, deployed, and observed healthy | Client/authorized release policy, protected deployer and independent smoke checks |

One approval never grants another. A client can request changes to technically passing work. A client can like a preview that still has a technical blocker. The lead explains the minimum relevant distinction without a long report.

## 2. Toolkit shipment checklist

- [ ] M1–M8 and all 33 task scenario groups have actual evidence; no hard-coded expected observations or empty artifact-path assertions substitute for execution.
- [ ] Claude and Codex adapters each load in fresh native sessions and their declared controller transports are exercised with real authorization, usage, tool, cancellation and resume events. A mock result cannot qualify a host.
- [ ] All-stack AI behavior is tested across the declared native/backend/model/polyglot/unfamiliar families. Platform-specific gaps remain visible; no forced JavaScript migration or claimed universal omniscience.
- [ ] Company responsibilities have real outputs and accountable assignments without a mandatory large swarm or artificial client meetings.
- [ ] An ordinary-language request, material question before any candidate, authenticated answer, active scope change, rendered result and client revision all work through the quiet console.
- [ ] Protected policy/evidence/signing/release storage is unreachable from workers and candidate code under actual attempted access. Same-user different folders or reviewer roles do not qualify.
- [ ] Evaluator tampering, required-test omission, replay, wrong-project/attempt/candidate evidence, stale results, malicious dependency/preview, prompt injection and privilege escalation are rejected in isolated tests.
- [ ] Crash/restart, rate limit, budget exhaustion, cancel races, duplicate callbacks, disk full, unavailable environment and failed deployment recovery preserve truthful state and bounded side effects.
- [ ] Whole-tree usage and budget reserves are measured. Missing counters are unknown, not zero. Native account and approved API billing are not silently interchanged.
- [ ] Installer/upgrade/uninstall/rollback work from installed paths containing spaces and Unicode, preserve unrelated configuration and client work, and declare migration limits.
- [ ] Native baseline / single-agent Client Mode / bounded multi-agent comparisons and held-out qualification meet predeclared criteria, with failures and task-family uncertainty reported.
- [ ] Source/artifact checksums, dependency/license inventory, supported versions, test report, runbooks, retention, support and incident ownership ship with the release.

## 3. Per-application checklist

- [ ] Every material required/excluded outcome is tied to the client's actual message; unresolved business policy is not silently guessed.
- [ ] The actual technology and version are preserved or a migration is authorized; each required component and interface is included in the candidate.
- [ ] Build and native/browser/API/data/model checks run in the right environment. Compile success does not replace user journeys; a browser view does not replace native or model-quality evaluation.
- [ ] UI/UX includes appropriate hierarchy, platform conventions, real controls, error/loading/empty states and declared accessibility checks. Real-user research is not claimed when only automated/model review occurred.
- [ ] Security, privacy, data migrations, duplicate actions, compatibility, resource/performance budgets and recovery are checked proportionately to the app's risks.
- [ ] External integrations are labeled mocked, sandbox-tested or production-tested correctly; secrets are not shipped in source, logs or test artifacts.
- [ ] Readiness evidence binds requirements, source, artifact, policy, environment, attempts, reports and relevant model/data versions. Relevant changes invalidate it.
- [ ] Client feedback and production approval are genuine, separately recorded and not written by a worker.
- [ ] The deployment plan identifies destination, cost implications, signing/store transformations, migrations, health probes and rollback/roll-forward constraints. Post-deploy checks target the actual release.

## 4. Staged go/no-go

G0: reviewed handoff/reference checks only. G1: implemented deterministic core. G2: protected verification and authority isolation. G3: real host capability. G4: client-to-result and feedback experience. G5: reliability/economics qualification. G6: base software release rehearsal. G7: real document/format operations. G8: company-service closure and complete v1.3 shipment.

A failing gate has an accountable engineer and a bounded remediation task. Missing paid access, device or environment is reported as blocked, not silently waived. Engineers may continue unrelated authorized work. Do not hold the client responsible for technical setup decisions that the engineering team can resolve.

The minimum release report contains version, tested scope, completed gates, evidence references, observed limitations and next material client decision. The normal client result can be a preview/package link and a few honest sentences. Detailed engineering evidence remains available internally.

## 5. Document and service shipment checks

- [ ] Document-only and build-from-file requests have independent correct routing; no fake code project is required to review a PDF or write a proposal.
- [ ] Real PDF/DOCX/XLSX/CSV/TSV/PPTX/image fixtures pass claimed read/review/edit/export operations with preserved originals, exact citations and explicit coverage.
- [ ] Required spreadsheet calculations use actual compatible computation; row-1,501/hidden-sheet/stale-cache cases cannot be reported complete without evidence.
- [ ] Edited artifacts reopen, preserve material meaning and declared editable features, and pass documented semantic/numeric/render checks. Full versus sampled visual review is explicit.
- [ ] Unsafe files, macros, external actions, parser/network/resource failures, forged document evidence and cross-project citations are rejected under actual isolated execution.
- [ ] Source revisions and access changes invalidate current derived conclusions/evidence and cached access; client instructions/answers survive pause, restart and feedback.
- [ ] Company responsibility outputs and risk gates are observable without a forced agent swarm; actual research remains distinct from inference.
- [ ] Support cases have genuine request/reproduction/resolution evidence; configured service coverage exists before promising monitoring or response. No role can sign contracts, purchase or contact customers without authorization.
- [ ] Documents, code, licensing/asset inventory, tested examples, installer/migrations and release notes match this exact version. The client receives working artifacts, not unreadable internal paperwork.
