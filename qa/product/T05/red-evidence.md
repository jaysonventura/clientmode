## Round 8 — the stores were created world-readable

The sandbox stops an untrusted check reaching the authority over a socket. It says nothing
about what another account on the machine can read straight off the disk, and until this round
nothing did. `auditPermissions` was added to the AT-005 observation and the gate went red on
the first run, naming the files:

```
not ok 1 - AT-005: Protected check registry and untrusted execution sandbox
"readable_by_other_accounts": [
  { "path": ".../verifier-authority",              "kind": "directory", "mode": "0755", "expected": "0700" },
  { "path": ".../verifier-authority/verifier.sqlite",     "kind": "file", "mode": "0644", "expected": "0600" },
  { "path": ".../verifier-authority/verifier.sqlite-shm", "kind": "file", "mode": "0644", "expected": "0600" },
  { "path": ".../verifier-authority/verifier.sqlite-wal", "kind": "file", "mode": "0644", "expected": "0600" }
]
```

Only the Ed25519 signing key had ever been protected — it was created at 0600 explicitly. The
protected policy store beside it, the approval record, the controller's state and the ingested
client documents were all created at the process umask.

### Mutations

| # | Mutation | Result |
|---|----------|--------|
| P1 | `ProtectedPolicyStore.open` creates the store with plain `mkdirSync` again | **still green** |
| P2 | no `secureStore` after opening, so the `-wal`/`-shm` sidecars keep their default mode | **red** |

P1 stays green because `secureStore` runs after the schema is in place and tightens the
directory as well as the files, so removing the create-time mode does not change the end
state the gate observes. It is kept as defence in depth: it closes the window between the
directory appearing and the post-open chmod, during which the schema is being written. That
window is not measured by any check here, and it is recorded as unmeasured rather than as
covered.

P2 is the load-bearing half. SQLite creates `-wal` and `-shm` on the first write, not at
creation, so a mode set only at open time never reaches them — which is exactly how the
original defect survived the one file (the signing key) that was written carefully.

### What this does not cover

The stores are owner-only, and the owner is the same OS user that runs the controller and the
untrusted checks. A compromised controller reads the signing key off the disk whatever the
mode is. Separating the verifier onto its own OS principal is a machine change that needs the
operator's decision, and it has not been made.
