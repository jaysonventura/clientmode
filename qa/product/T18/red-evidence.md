## Round 2 — the operator surface, added after the first client-readiness pass

`commands_match_operations_contract` used to check only that the declared surface matched the
operations contract. Nothing ran the commands. Seven of the thirteen — `pause`, `resume`,
`cancel`, `verify`, `export-evidence`, `rollback`, `upgrade` — were declared and had no terminal
entry point at all.

The gate now invokes every command for real, in its own state home, with a well-formed request
naming something that does not exist. Three things are asserted:

- none exits `missing_capability` from the dispatcher, which is what an unwired command returns;
- every exit code is one the contract defines;
- none exits `internal` — a crash is not an answer to "no such candidate".

It also opens one project from six processes at once, and a fresh state directory from eight
processes released at the same wall-clock instant.

| # | Mutation | Result | What it proves |
|---|----------|--------|----------------|
| `S1` | `pause` loses its terminal entry point | **RED** | an unwired command is caught |
| `S2` | every open takes the exclusive controller lock again | **RED** | the lock belongs to the run loop, not to a `status` call |
| `S4` | a missing candidate reported as an internal error | **RED** | `internal` is not an answer |
| `S6` | `busy_timeout` set after `journal_mode` again **and** the retry removed | **RED** | pragma ordering is what makes a simultaneous open survivable |
| `S3` | the per-migration re-check inside the write transaction removed | green | second layer; `BEGIN IMMEDIATE` already serialises them |
| `S5` | the busy retry removed | green | second layer; correct pragma ordering alone is sufficient |
| `S7` | both bootstrap re-checks removed | green | same — they are belt-and-braces over the transaction |

### Three real bugs this round found

1. **Seven commands were declared and unrunnable.** Now wired to the modules the gates already
   exercise, each returning a contract exit code.
2. **Two terminals in one project crashed one of them.** The state-directory lock was taken on
   every open, not just by the process that owns the run loop. Six concurrent `cm status` calls
   produced one crash; now all six answer.
3. **`PRAGMA busy_timeout` was set after `PRAGMA journal_mode = WAL`.** The statement that waits
   longest is the journal switch, and it ran before the timeout that would have let it wait. Eight
   processes opening a fresh project at one instant: **all eight failed**. All eight now succeed.
   The barrier is what exposed it — spawning processes and hoping they overlap is not a race test,
   because startup latency staggers them and the first has finished migrating before the second
   begins.

### A flaky gate, caught and fixed

The first version ran all fourteen invocations against one shared state home. `rollback` then
sometimes found a snapshot that the parallel `upgrade` had just taken, and answered 0 instead of
2. Each command now gets its own home: a gate whose answer changes between runs is measuring the
scheduler, not the code.


## Round 5 — the install's own health

`cm doctor` reported on the hosts and said nothing about the install it was running from. Three
things go wrong quietly after a successful install, and none of them announce themselves: the
bundled toolkit falls behind the source it was built from, the launcher points at a directory
somebody deleted, and the skills copied into the host's directory drift from the ones the toolkit
ships. Each shows up later as behaviour the client cannot explain.

`checkInstall` now runs first, every finding names a file and the command that fixes it, and a
broken install makes `doctor` exit `missing_capability` rather than reporting a clean bill.

| # | Mutation | Result | What it proves |
|---|----------|--------|----------------|
| `H1` | a missing toolkit is no longer reported | **RED** | the first thing to check is whether there is an install at all |
| `H2` | a launcher pointing at a deleted toolkit passes | **RED** | the state a client reaches by moving a folder |
| `H3` | a host with no Client Mode section is called healthy | **RED** | skills present and instructions absent means the host loads none of it |
| `H4` | findings no longer carry a remedy | **RED** | a check that reports a problem without saying what to run has moved the work, not done it |
| `H5` | a broken install is still a passing doctor report | **RED** | an exit code that says fine to a script is worse than the text that says otherwise |

`H3` and `H5` were green at first, because nothing asserted them: the fixture did not require
`INSTRUCTIONS_MISSING`, and no assertion looked at `doctor`'s exit code at all. Both are now
checked.

### A gate that could not tell two answers apart

The unwired check used exit code `missing_capability` as its signal. Once `doctor` started
returning that same code for a genuinely broken install, a correctly wired command looked
unwired. Exit codes cannot carry that distinction — both answers are honest for what they
describe — so the check now reads the dispatcher's own sentence instead.
